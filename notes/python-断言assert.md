## 一、本课立住的机制（誊自本人口答）

### 1）`-O` 剥除与"必须无条件生效"的检查（Q1）

- `python -O` 启动 → 断言整套被跳过（剥除）。
- 本人给的四类"**绝不能用 assert 来守**"的检查：

| 类型 | 例子 | 为什么不能用 assert |
|---|---|---|
| 用户输入校验 | `assert isinstance(user_input, str)` | 生产环境可能被 `-O` 移除，非法输入会直接进入业务逻辑 |
| 安全检查 | `assert has_permission(user)` | `-O` 下权限检查消失，等于没有 |
| 业务规则 | `assert amount <= balance` | `-O` 下余额不足也能转账 |
| 数据完整性 | `assert len(data) > 0` | `-O` 下空数据也能继续处理 |

- **本人收口原话**："因为这些检查一旦失效，程序会**静默地做错事**，而不是报错。**这比直接崩溃危险得多。**"
- **AI 补（2026-09-15 教练侧实测互证，非本人口答）**：`-O` 的连带效应不止断言那一行——它同时把 `__debug__` 置为 `False`，于是 `if __debug__:` 包住的**整块代码一起蒸发**：
  - `python o_test.py` → `AssertionError: 断言守的这条在 -O 下会消失`，exit 1
  - `python -O o_test.py` → **静默跑完**、断言之后那行照常打印，exit 0
  - `if __debug__:` 分支：默认可见；`-O` 下整块不执行
  → **"会被 `-O` 悄悄关掉"不是 `assert` 一个关键字的属性；凡是挂在 `__debug__` 上的东西都是同族。**
  → 实验原件：`.workbuddy/tmp/o_test.py`、`.workbuddy/tmp/o_test2.py`

### 2）试金石判据（Q2，本人原话）

> "**如果把这条检查删掉，程序逻辑会变吗？** 不会变 → 用 assert，它是'开发者的自我提醒'，删了不影响正确性；会变 → 必须用 raise，它是'业务逻辑的一部分'，删了程序就错了。"

当场判新场景（本人自答五例）：

| 场景 | 判据落点 | 结论 |
|---|---|---|
| 快排开始前 `len(arr) > 0` | 空数组是合法输入，删了逻辑不变 | assert |
| API 收到 `age` 字段，要求 0–150 | 外部输入，删了非法数据会入库 | **raise ValueError** |
| 二分查找循环里 `lo <= hi` | 内部不变量，删了逻辑不变 | assert |
| 文件读取后 `content is not None` | 文件可能为空是正常情况 | **raise** |
| 缓存字典更新后 `key in cache` | 内部状态断言，删了逻辑不变 | assert |

### 3）assert 是语句、不是函数——逗号陷阱与括号陷阱（Q3＋Q4，本人原话）

- 语法是 `assert 条件, 消息`，**没有括号**；逗号是 assert **语句语法**的一部分，用来分隔条件与消息。
- 正确：`assert x > 0, "x 必须为正"` → 失败时 `AssertionError: x 必须为正`。
- 错误（想当然加括号）：`assert(x > 0, "x 必须为正")` → **不报错，但断言永远为真**。原因：assert 后面跟的是一个**表达式**，而 `(x > 0, "x 必须为正")` 是一个**元组**（两个元素）；**元组只要非空，布尔值就是 `True`**，所以条件恒真、即使 `x > 0` 为 `False`。
- 本人对照表：

| 写法 | 解析成什么 | 实际效果 |
|---|---|---|
| `assert x, "消息"` | 语句；条件＝`x`，消息＝`"消息"` | `x` 为假时抛 `AssertionError: 消息` |
| `assert(x, "消息")` | 语句；条件＝**元组** `(x, "消息")` | 元组非空 → 条件恒 `True`，**永远不抛异常** |

## 二、现场记录：assert 在测试里就是正确选择（Q5，誊自本人口答）

MP1 三套测试（`test_parse_sessions.py` 24 例／`test_render.py` 8 例／`test_aggregate.py` 9 例）为什么用 assert 而不写 `if ...: raise`——本人五条理由：

1. **测试代码本来就不会用 `-O` 跑**——测试是开发阶段的事，没有理由用优化模式运行，所以"assert 被移除"的风险在测试场景中为零。
2. **assert 的语义就是"断言"**——测试用例的核心就是"我断言这个结果是对的"；`assert` 关键字直接表达测试意图，比 `if not ...: raise` 更清晰。
3. **测试框架会增强 assert**——pytest 会自动重写 assert 语句，失败时显示完整的表达式值和中间结果；`if ...: raise` 没有这个待遇。
4. **`if ...: raise` 在测试里是噪音**——用例的重点是"期望什么"，不是"如果不对怎么报错"；`raise AssertionError` 是重复劳动，`assert` 一步到位。
5. **在测试里 assert 就是"必须无条件生效"的**——因为测试环境永远不会开启 `-O`（可在 CI 配置里保证），所以"会被移除"这个缺点在测试场景不构成问题。

> **AI 存疑项（未核，故意不写成事实）**：第 3 条里"pytest 重写后的断言，在 `-O` 下还算不算数"——教练**没测过**。它不影响本课结论（第 1、5 条已独立成立），但"重写后的 assert 是否仍依赖 `__debug__`"是**可查的**，留作候选实验，核过再写进正文。
