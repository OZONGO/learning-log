## 一 · 五子系统：定义、职责与评判标准

### 1.1 harness 的定义与界划（A1）

**定义：harness = 模型权重之外的一切工程基础设施**——指令、工具、环境、状态、反馈五个子系统，全部由人写、人维护、写在仓库里。

**界划在"权重与代码的分界线"上：**

| 侧 | 归属 | 判据 |
|---|---|---|
| 会随模型升级被重新训练进参数里的东西 | 模型能力 | 你无法用工程师的手去改它，改它靠训练 |
| 要靠人写下来、放进仓库、由 agent 读取执行的东西 | harness | 会丢、会过期、会写错，因而可被工程改进 |

**为什么这条界划必须存在**：课程要回答的问题是"为什么有能力的 agent 仍然失败"。只有把界划画在权重之外，这个问题才成立——失败发生在**权重之外**（能力鸿沟 vs. 验证缺口／诊断循环）。反过来说，**"模型更强"修不好"验收标准没写下来"**：前者是参数问题，后者是仓库里少了一行字。界划一模糊，所有失败都会被归因成"模型不够强"，工程就无从下手。

### 1.2 五子系统及各自职责（A2）

| 子系统 | 一句话职责 |
|---|---|
| **指令（Instructions）** | 告诉 agent 这是什么系统、怎么验、什么不许做 |
| **工具（Tools）** | 给 agent 能真正动手的手段（shell／文件／测试），并按最小权限约束 |
| **环境（Environment）** | 让"跑起来"可重现（依赖锁定、运行时版本） |
| **状态（State）** | 让跨会话知道"现在做到哪了" |
| **反馈（Feedback）** | 给出**一条能跑的命令**，让 agent 自己判断对不对 |

**判为"投入最少、回报最高"的是反馈子系统。**

理由在于**缺失后果的量级差**：其余四个缺了，后果是"效率低"——agent 多花时间摸索、多问几句、跑错一次重来。反馈缺了，后果是**"不知对错还能宣布完成"**——它同时是唯一能自我纠错的通道，一旦缺席，前面四个子系统的输出全部失去校验。而它的成本只是**往指令文件里写一行真命令**：投入是一行字，回报是整条纠错回路。

### 1.3 两张表的对应关系：多对多（A3）

**两张表回答的是不同维度的问题：**

- **五子系统（L02）回答"harness 由哪些部件组成"**——一张**静态结构表**：有哪些格子，格子怎么分。索引维度是"**东西**"。
- **六失败模式（method-map）回答"实际坏掉时是什么症状、先修哪个"**——一张**症状→处方表**：按现象索引到"首要修复"和"主要工件"。索引维度是"**坏法**"。

**对应关系是「多对多」，不是一对一：**

- **一枚失败模式通常要几个子系统协同**。例："提前宣布完成"要靠 反馈（给出可跑命令）＋状态（记录当前真实进度）＋指令（写死完成定义）三条同时在场，缺一条这枚失败模式就会复发。
- **一个子系统同时防几枚失败模式**。例：状态子系统既防"新会话摸黑"，也防"交接薄弱"。

**背一张不等于会另一张**：因为**索引维度不同**。你背下五个子系统名，遇到"agent 说完成了但没跑过测试"，仍不知道该翻哪一格——因为症状表问的是"这属于**哪枚失败模式**"（→ 提前宣布完成），不是"这属于**哪个部件**"。反向也一样：知道这枚失败模式叫"提前宣布完成"，不等于知道该动哪个部件（这里要同时动三个）。

**两张表要配对使用**：结构表告诉你"有哪些零件可供调遣"，症状表告诉你"这次该调哪几个"。课程的使用原则是——**按失败模式索引，补最能直接消除当前那个失败模式的那一个工件**。

### 1.4 反馈子系统的判据：为什么退码要只看 CRITICAL（C12 · C13）

#### 1.4.1 计数与证据不一致：谁变成了说谎的裁判（C12）

> **实测锚点**：2026-10-09，`mini-projects/mp1-weekly-report/harness-lab/strong/check.py`（171 行，HEAD `9a87d08`），`py -3.13` 实跑。

**先说当前实物的真实结构**：`check.py` 全文**不存在** `fail()` 计数器、`CRITICAL_FAIL`、`RECS` 或 Summary 栏；计数是 `failed = []` **逐条 append**（第 152–162 行），汇总直接 `len(failed)`（第 165 行），退码 `return 1/0`（第 166/168 行）。也就是说——**当前这版是"逐条累加"的良好实现**，正是本问所推崇的形态。

那么本问所指的机制在**当前这版里以什么形态存在**？答案是：**位置解耦**。

```python
    suite_ok, suite_msg = run_mp1_test_suite()
    print(("PASS: " if suite_ok else "FAIL: ") + f"[MP1 测试套件] {suite_msg}")   # 第 141 行：先打印
    ...
    for name, fn in checks:                     # 第 153 行起：后计数
        ...
        else:
            print(f"FAIL: [{name}] —— {reason}")
            failed.append(name)                 # 第 159 行
    if not suite_ok:
        failed.append("MP1 测试套件")            # 第 162 行：计数追加在最末
```

**关键点**：套件项的**打印位置（第 141 行）**与**计数位置（第 162 行）**相隔 21 行、跨越整个断言循环。当前的正确性靠"`append` 恰好接上了 `print`"来保证——**打印与计数是两条独立的代码路径，只是这次巧合地对齐了**。这正是"计数器与证据可能不一致"的结构性土壤；一旦后续有人在第 141 行与第 162 行之间插入一条只有 `print` 没有 `append` 的分支（或反之），两者立刻分家。

**实测佐证（当日输出，产物为 9/25 遗留的旧形状文件）：**

```
PASS: [MP1 测试套件] MP1 测试套件全过（解释器 ...Python313\python.exe）
PASS: [D1a 顶层为 object]
FAIL: [D1b week_items 为 list[object]] —— week_items[0] 应为 object，实际是 list：['W1', 7.2]
FAIL: [D1b category_items 为 list[object]] —— category_items[0] 应为 object，实际是 list：['语法', 14.799999999999997]
FAIL: [D2  中文以 UTF-8 原文在场] —— 产物原始字节未含 UTF-8 原文"语法"
FAIL: [D3  仅含 W2] —— 无法提取周次：week_items[0] 不是 object，原形 ['W1', 7.2]——修完形状后再判范围
```
`stdout` 打印 4 条 FAIL；`stderr` 报 `4 项未过。`；`EXIT=1`——**当前这版三者一致**（套件 PASS 故未进 `failed`，计 4 条）。这恰好反证了判据：**一致是应该的，不一致才是故障。**

**对不上的时候，说明什么？** 说明**计数器不是从证据里数出来的，而是有人手写的一笔**。一旦如此，汇总栏与打印明细就**各自独立、可以各说各话**——没有一个数字能追溯到具体某条 FAIL 行。

**为什么比单纯误报更危险——因为误报是"裁判看错了"，计数不一致是"裁判在说谎"：**

| | 单纯误报 | 计数与证据不一致 |
|---|---|---|
| 发生层级 | **单条**证据 | **汇总**层面 |
| 用户的应对 | 能看到原文，可自行判断、可不信 | Summary 正是人**唯一信任、不再核对**的那一栏 |
| 后果 | 那一条判断错了 | **得到一个任何一条证据都不支持的数字** |

**"让谁变成说谎的裁判"——让汇总栏说谎：** 人看打印明细时会逐条读，看汇总栏时图的就是省事、直接采信。所以汇总栏拿到了**无需证据即可签发结论**的权力。这种工具同时具备双面性：

- 能**多报**（分母虚高，让两个不可比的比值被拿去比较）；
- 能**少报**（手写一笔掩盖真实失败数）。

**最后一条，也是最重的一条**：**能让裁判说谎的工具，会污染所有依赖它判断的下游决策。** 我给 `check.py` 写下的两条纪律——"**检测必须接进判定：每条 check 的失败写进 failed 列表，最终由退出码裁决**"与"**反馈质量线＝零沉默＋零诬陷**"——正是针对这一点。**计数器必须永远只是证据的一次机械折叠。**

#### 1.4.2 退码为什么只看 CRITICAL（C13）

> **锚点说明**：本题问的"审计脚本"在仓库中的实物是 `docs/learn-harness-engineering/tools/audit-harness.sh`（544 行；其实现与实跑记录见 `mini-projects/mp1-weekly-report/harness-lab/audit-2026-09-29.md`）。**本人在 2026-10-09 重读了该脚本的计数与退码段（第 30–64、512–544 行）予以核对。**

**实物退码逻辑（`audit-harness.sh` 第 535–543 行）：**

```bash
if [[ $CRITICAL_FAIL -gt 0 ]]; then
  echo -e "CRITICAL items are missing. Address these before running long agent sessions."
  exit 1
else
  echo -e "All CRITICAL harness components are present."
  [[ $RECOMMENDED_FAIL -gt 0 ]] && echo -e "Some RECOMMENDED items are missing. See above for specific fixes."
  exit 0
fi
```

**只看 CRITICAL 的理由——退码是布尔判决，必须有稳定语义：**

退码只有"过/不过"两态，因此它必须承载**与仓库形态无关的固定底线**。CRITICAL 的定义正是"**must-have for basic function**"——这个集合**不随仓库内容变化**，任何仓库都适用同一把尺子。Summary 也据此分栏：`Critical: x/7 (must-have for basic function)` vs `Recommended: y/z (best practice)`。

**而全量命中数的分母是浮动的——这不是推测，是实测：** 同一份脚本，`audit-2026-09-29.md` 记录两跑得到 **`0/65`** 与 **`5/72`** 两个不同分母。差额 7 项来自**分支被触发**：`AGENTS.md` 存在时进入内容检查分支（净 +5：文档 staleness 规则／commit 原子性规则／入口文件 50–200 行／入口文件链接 docs/／硬约束带 source-why 注释），`feature_list.json` 存在时再触发两处闸门（净 +2：必需字段／VCR 比率）。若 `PROGRESS.md` 也存在，分母会到 **73**。

**（该记录中另有一条与本题强相关的读码事实）**：主目录跑的 `Critical` 失败数报 7，而打印与 `What to fix` 清单各只有 6 条——差额来自第 150–154 行的 `else` 分支：那里 `fail()` 是裸调用（不进 `RECS`、不加计数），紧接着手动 `CRITICAL_FAIL=$((CRITICAL_FAIL + 2))`。**这正是 1.4.1 所述"计数不是逐条累加、是手加的一笔"的真实样本**，发生在审计脚本自身（而 `strong/check.py` 反而是逐条累加的良好实现——两处对照见 1.4.1）。

**若全量命中数也进退码，会出三件事：**

1. **退码失去可复现性**——同一份代码，仅因为**多写了一个 `AGENTS.md`**，就多出 7 项要过；同仓库在不同配置下退不同的码，"通过"不再是代码的属性。
2. **与"通过"解耦**——`Critical: 7/7` 本已代表"底线守住"，掺进 Recommended 后，一个 harness 健全的仓库会因为缺少一条**最佳实践**而永远红灯。底线与建议被压进同一个信道，绿灯的含义被稀释。
3. **产生反向激励（Goodhart 定律）**——为刷绿码，agent 会去补**不重要但好补**的 Recommended 项（比如给入口文件加一行注释凑够 50 行），而不是修真正让它卡住的那一处。**指标一变成目标，就不再是好指标。**

**所以设计是「双信道」**：退码裁决 CRITICAL（底线，`exit 1`）；Recommended **只打印、附修复建议、进退码**（`warn` + `RECS`）。让绿灯的含义始终是"**底线守住了**"，而不是"**你写得够多**"。

**迁移到自己体系**：这正是"**验证命令的退码必须承载稳定语义**"的同一条纪律——`check.py` 的 0/1/2 三段（全过／断言失败／不可读）也是这个思路：**退码只回答"能不能继续"，不回答"有多好"**。

## 二 · 六失败模式 ↔ 工件对照

### 2.1 六失败模式逐行（A4）

| 模式名 | 实际表现 | 首要修复 | 主要工件 |
|---|---|---|---|
| **新会话摸黑** | 新会话花大量时间重新摸索状态和启动方式 | 让仓库成为唯一事实来源 | `claude-progress.md` |
| **范围蔓延** | 一次启动多个功能，最后没有一个完整收尾 | 限制当前活跃范围 | `feature_list.json` |
| **提前宣布完成** | 代码改了就说"完成了"，但没有可运行证据 | 把完成绑定到验证证据 | `clean-state-checklist.md` |
| **启动脆弱** | 每轮会话都要重新学怎么启动项目 | 统一启动与验证路径 | `init.sh` |
| **交接薄弱** | 下一轮看不出哪里可用、哪里坏了、接下来做什么 | 明确写交接摘要 | `session-handoff.md` |
| **评审主观** | 质量判断依赖个人记忆和感觉 | 用固定维度做评分 | `evaluator-rubric.md` |

### 2.2 巨型指令文件是反模式：四条危害与判据（B8）

**四条机制性危害（课程 L04"巨型指令文件陷阱"）：**

1. **上下文预算被挤占**——规则吃掉的 token，就是留给实际任务的 token；
2. **"中间迷失"（Lost in the Middle）**——长文件**中段**的内容最容易被忽略，而堆规则永远是往中段堆；
3. **优先级相互冲突**——后加的规则与前文的规则打架时，agent 无法判断谁优先；
4. **维护衰减与矛盾累积**——没人会读完 500 行再改，于是矛盾只增不减。

**共同后果**：**指令信噪比下降**。规则越多，**每一条**被稳定遵循的概率越低——这是"越多越弱"，不是"越多越保险"。

**正确动作**：**按失败模式索引，补最能直接消除当前那个失败模式的那一个工件。**

判据（三条）：

1. **入口文件是路由器，不是百科全书**——课程给的量级是 **50–200 行**；它负责"指路"，不负责"装货"（主题内容按需展开到 `docs/`）；
2. **每条指令带三个元数据**——`source`（凭据）／`why`（适用条件）／`remove when`（过期条件）；
3. **一次只补一处**——新规则若说不出它消除哪枚失败模式、在什么条件下该删，就不该加。

**注**：这套判据我在自己的体系里也有对应收口——`06-每周复盘模板.md` 第四节月度复盘第 6 问："本月文档新增了多少条规则/检查项？有没有能合并或删除的？（指令越多越难被稳定遵循——文档体系本身也是一个 harness，警惕规则膨胀）"。

### 2.3 真命令 vs 判据清单：判分权归谁（B9）

**机制是「判分的自由裁量权归谁」。**

**真命令**：退出码是一个**不依赖解释的布尔值**。任何人、任何 agent、任何时刻跑同一条命令，得到**同一个真值**。判分过程是**机械的**——不需要理解、不需要判断、不可能"理解偏了"。

**"判据清单"／"应当检查 X"**：是**自然语言断言**，要判定它，必须**再解释一次**。而解释权落在**判分者**手里。当判分者就是干活的人自己（agent 自评／人自评）时，它有三种方式把红读成绿：

- **降级解读**：把"应当检查编码是否正确"读成"我看了一眼，没问题"；
- **模糊措辞**：把"没通过"写成"基本通过"、"待完善"；
- **口径漂移**：这次按严格口径判，下次按宽松口径判，而"应当检查 X"本身没有规定口径。

于是**验证退化成自我声明**——这正是"**验证负债**"：停止条件不可自动检查，就等于没有停止条件。

**一句话收口**：真命令把**判分的自由裁量权从人手里拿走，交给机器**。这也是"generator / evaluator 必须分离"的底层原因——只要判分者与干活者同体，且判据是可解释的自然语言，"自己判自己"就必然趋向宽松。写死命令是**在判据层面**切断这条路径（在结构层面切断靠角色分离）。

### 2.4 WIP=1 属"范围蔓延"的修复（B10）

**判据差在「衡量什么」：**

| | 效率优化 | 范围蔓延的修复 |
|---|---|---|
| 衡量对象 | **单位时间产出**（做得多快） | **同时活跃数** ＋ **已验证完成率（VCR）** |
| 优化方向 | 提高吞吐 | 降低并行度、逼出收尾 |
| WIP=1 是否提升它 | **不提升**（常使单点看起来更慢） | **提升**（把"一个都没收尾"变成"逐个收尾"） |

**为什么 WIP=1 属于后者**：它**不改变任何单步的速度**——你写同一个功能还是那么快。它改的是"**同时开几个**"。而"范围蔓延"的病灶正是"一次启动多个功能，最后没有一个完整收尾"——是**范围**问题，不是**速度**问题。

**数据支持**：

- 使用"小下一步"策略（等价 WIP=1）的 agent，**任务完成率比宽泛提示高 37%**；
- **代码行数与完成功能数呈弱负相关**——写得多 ≠ 完成得多。这直接证伪"多做并行＝效率高"的直觉。

**判据的可操作形式**：当 **VCR < 1.0**（有 active 但没 passing）时，**阻止开新任务**。这条闸门衡量的是"活跃数/完成率"，与单位时间产出无关——所以它是范围之手，不是效率之手。

## 三 · 拆件实验的正确读法：拆除结果 ≠ 瓶颈归因

### 3.1 为什么"降幅最大"不能单独证明瓶颈（B6）

**因为这个实验只回答"当前这批任务下，哪个组件最有价值"，不回答"系统为什么卡住"。**

两个偏差来源：

1. **任务分布偏差**——降幅是相对**你跑的那批任务**测出来的。恰好重压某组件，降幅就大；换一批任务，排序会翻。它测的是"组件与当前任务的相关度"，不是"系统的瓶颈"。
2. **替代性干扰**——某组件降幅大，可能是它**独占**了某个功能（拆了就没替代），而不是因为它对应真正的瓶颈；反之某个组件降幅小，也可能是它有冗余路径兜着（详见 3.2）。

**要补的证据是失败记录与归因**（五层防御）：

| 层 | 问的问题 |
|---|---|
| 任务规范 | 任务是不是没说清楚？ |
| 上下文供给 | 该在的信息是不是没给到？ |
| 执行环境 | 环境是不是不可复现？ |
| 验证反馈 | 是不是缺一条能跑的命令？ |
| 状态管理 | 是不是状态断裂了？ |

做法：**先看失败实际发生在哪一层，把拆除实验的结果作为辅助证据**，而不是反过来拿降幅大小直接指认瓶颈。课程原文定调：这个实验"**回答的是'当前哪个组件最有价值'，不能单独证明'瓶颈在哪里'**"。

### 3.2 "拆除后几乎没影响"的三种解释（B7）

**三种解释：**

1. **冗余**——功能被另一个组件重复覆盖了，拆掉一个还有备份顶上；
2. **设计失效**——它本来就写错了／没接上线，从头到尾没真正起作用；
3. **尚未被当前任务充分触发**——这批任务没走到需要它的地方，换对任务它就有价值。

**为什么"没有影响"推不出"无用"：**

关键在于**两者断言的层次不同**：

- "**没有影响**"是关于**当前任务分布的一次观测**——"在这批任务里，拆了它，表现没变"。
- "**无用**"是关于**组件本身的属性判断**——"它在任何情况下都不产生价值"。

**观测只能否证"当前任务下有用"，不能否证"在其他任务分布下有用"。** 统计学上这叫"证据不足"而非"证据为负"；工程上这就是把"我没看见"报告成"不存在"——而这三条里第 3 条（没被触发）和第 1 条（冗余）都意味着**它可能仍然有用，只是这次没轮到它**。

**迁移**：这一条与我在 `strong/check.py` 里写下的纪律直接对应——"**诊断要么报真相、要么承认'无法提取'——不许把'我没看见'报告成'不存在'**"（见 `check_week_scope_w2`：拿不到 `week` 键时返回"无法提取周次……原形 {it!r}"，而不是静默过滤后报一个捏造的空集）。

### 4.2 五子系统在 MP1 里的实物（C11）

**对象**：`mini-projects/mp1-weekly-report/`（MP1 周报生成器 v1.x，纯标准库）。

| 子系统 | MP1 里的实物 | 判定 |
|---|---|---|
| **指令** | 根目录只有 `README.md`（六节：做什么／输入 输出／架构／进度／怎么用／已知技术债），**无 `AGENTS.md` / `CLAUDE.md`** | **无，真债**。README 面向人读，AGENTS.md 面向 agent 读；缺它，agent 第一件事就是自己猜"这系统是什么、怎么验"。直接对上"隐性约定没写下来，agent 无从遵守" |
| **工具** | 无 `.claude/settings.json` / `mcp.json` 权限声明；本地 shell、文件读写、`py -3.13` 均可；`harness-lab/strong/check.py` 是一把自带的反馈刀 | **权限声明无，故意不要**。判据：单人本地项目、无多 agent 并行、无敏感写盘操作，权限隔离不增加可靠性 |
| **环境** | 无 lockfile、无 `.python-version`、无 Makefile；README「怎么用」给了 `py -3.13 generator.py` 等命令 | lockfile **故意不要**（零第三方依赖，写了不提供额外可复现性）；`.python-version` **真债** |
| **状态** | 无 `PROGRESS.md` / `DECISIONS.md` / `feature_list.json`（**注**：`harness-lab/strong/feature_list.json` 是实验用靶，非项目状态件）；README「进度」节是静态清单 | **无，真债**。README 进度节是"历史快照"，不是"当前状态"；每会话不更新、下会话不读，等于每次从零摸 |
| **反馈** | `python -m unittest discover` 跑出 **60 例全绿**；`harness-lab/strong/check.py` 有退码契约（0/1/2）；但**验证命令没写进任何指令文件**，也无 Makefile `check`/`test` | **有事实、缺入口，真债**。反馈子系统不是"有没有测试"，是"agent 能不能一眼拿到一条命令跑出绿灯"——入口不写进 AGENTS.md，agent 仍要自己拼命令、自己猜哪些必须跑 |

**"故意不要"分别对应哪枚失败模式：**

| 故意不要的项 | 对应的失败模式 | 说明 |
|---|---|---|
| **lockfile**（`requirements.txt` 等） | **启动脆弱** | lockfile 防的是"环境不可复现"。本项零依赖，故不构成风险 |
| **`.python-version`** | **启动脆弱** | 同上，钉的是运行时版本 |
| **进度文件**（`PROGRESS.md`） | **新会话摸黑** | 进度文件防"下个会话从零摸索" |

**"故意不要"什么时候成立、什么时候只是遗忘——判据自给：**

> **成立 ⟺ 你能写出「缺了它，成本体现在哪里・当前为什么不构成风险・什么条件一变就必须补」。**
> 写不出这三条 = **遗忘**（只是没做，却给自己贴了"故意"的标签）。

**三条判据的现成样本（对比出判据的锋利处）：**

| 项 | 缺了它的成本 | 当前为何无风险 | 触发条件 | 判定 |
|---|---|---|---|---|
| lockfile | 环境漂移 | **零第三方依赖**，标准库即可复现 | 依赖不再为零 | **故意不要成立** |
| 权限声明 | 越权写盘 | **无并行 agent、无敏感写盘** | 引入多 agent／写盘操作 | **故意不要成立** |
| `.python-version` | 解析器行为静默漂 | **不成立**——`__pycache__/` 里 313 与 314 的 `.pyc` **并存**，是"同一份源码被两个解释器先后编过"的物证 | —— | **真债**（风险已现形） |

**判据的关键**：第三条是本判据最好的样本——**"故意不要"必须建立在"风险当前不存在"之上；一旦有了物证证明风险已现形，它就自动从"故意不要"降格为"真债"。** 判据不是一次性的辩解，是要接受现实检验的。

**配套：每条"故意不要"必须挂触发条件**（何时必须补）——`.python-version`／虚拟环境 → **MP2 第一次 `pip install`**（T33 已定，10/12 落地）；lockfile → 依赖不再为零；`PROGRESS.md` → 单任务跨两个以上会话；AGENTS.md 验证命令节 → MP2 开始由 agent 参与写码。
